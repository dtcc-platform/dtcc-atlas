Upload Wizard Mockups

Storyboard visuals for team alignment: upload - detect - confirm - ingest - use.

Frame 1 - Entry Point In Atlas
Discoverable
DTCC Atlas / Datasets
Draw Area Upload Data
New upload action sits next to existing dataset workflow controls.

This first screen focuses on placement and intent. The user is already in the context where data work begins, so `Upload Data` is placed beside existing dataset actions instead of hidden in an admin menu. The goal is to signal that uploaded data is not a secondary feature but part of the same core workflow as drawing an area and selecting datasets. At this step, the user only needs to decide to start uploading; the system should not ask for technical details yet.

Frame 2 - Add Files / Folder
Low Friction
Drop files or a folder here
Supports mixed geospatial inputs, zipped packages, and sidecar file groups.
Browse Files Browse Folder

Here the user performs a simple collection task: provide everything relevant in one gesture. Supporting both directory and multi-file input reduces friction for realistic geospatial deliveries, where data usually comes as bundles rather than single files. The system should preserve the original file structure, detect related sidecar files, and build an internal upload batch before any destructive processing. The design keeps this step deliberately forgiving so users can start fast and refine later.

This review screen is where "automagic" becomes transparent. The user sees how the system grouped files into dataset candidates, what type was inferred, and which assumptions are uncertain. Confidence and warnings are critical because users need to trust automation without losing control over edge cases. Internally, the platform is combining suffix checks, content inspection, and parse attempts to produce these suggestions, but the UI presents the output in operational language that supports quick decision making.

This step handles ambiguity explicitly. The user confirms naming, semantic role, and CRS so Atlas can ingest data safely and route it correctly later for simulation, analysis, and visualization. Instead of forcing everything as mandatory from the start, only high-impact unresolved items are highlighted for intervention. The system uses these confirmations to generate deterministic ingestion metadata, avoiding hidden assumptions that could cause silent downstream errors.

Ingestion is represented as a staged job, not a black box. The user can see where time is spent and which datasets succeeded, failed, or are waiting on input. This is essential because uploads may be large, heterogeneous, and only partially valid, so all-or-nothing feedback would be frustrating and operationally expensive. The system should keep per-dataset state, surface actionable errors, and allow targeted retry without redoing successful work.

The completion screen closes the loop by immediately connecting ingestion to usable outcomes. The user can open uploaded datasets in the same Atlas surfaces used for built-in sources, which reinforces the first-class data model. Source and role badges preserve provenance and make routing decisions inspectable when multiple data origins are available. From a product standpoint, this screen is where upload stops being an import utility and becomes a capability that changes daily workflow.
